## 1. Role and request workflow

A web server accepts HTTP messages, selects the relevant host and route, serves public files or delegates processing to an application, and returns an HTTP response. A typical flow is DNS resolution, transport connection, TLS negotiation when applicable, request parsing, routing, authentication/authorization where required, resource handling, response and logging. DNS maps names to network addresses; TCP provides reliable ordered delivery; TLS protects communications; HTTP describes requests and responses.

HTTP defaults to port 80 and HTTPS to 443. HTTP/1.1 and HTTP/2 normally use TCP; HTTP/3 uses QUIC over UDP. Ports 8080, 8443, 5000 and 3000 are common conventions for particular development or alternate services, not mandatory assignments.

```text
Browser -> web server -> static content
                      -> application -> database
Browser <- HTTP response <-------------+
```

A static file can be delivered directly. Dynamic output is generated by an application. Core source code, configuration, database files and secrets must not be exposed as public files.

## 2. HTTP messages

Illustrative HTTP/1.1 request:

```http
GET /api/attendance/42 HTTP/1.1
Host: localhost:5000
Accept: application/json

```

GET retrieves a representation; the request target identifies the route; HTTP/1.1 is the protocol version; Host identifies the target authority; Accept expresses a preferred response media type. The empty line ends the header section.

Illustrative response:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 9

{"id":42}
```

The status line gives the protocol, status code and optional HTTP/1.1 reason phrase. Content-Type describes the body format; Content-Length is its byte length. HTTP/2 uses a :status pseudo-header rather than a textual reason phrase. Headers are metadata, while the body carries representation data.

## 3. Status codes and semantics

| Class | Meaning |
| --- | --- |
| 1xx | Informational interim responses |
| 2xx | Successful request handling |
| 3xx | Redirection or further client handling |
| 4xx | Client-side request errors or refusals |
| 5xx | Server-side failure |

| Code | Name | Original example |
| --- | --- | --- |
| 100 | Continue | Client may continue transmitting request content |
| 200 | OK | Retrieve an attendance record |
| 201 | Created | Successfully create a resource |
| 202 | Accepted | Report generation queued, not yet completed |
| 204 | No Content | Successful deletion without response content |
| 301 | Moved Permanently | Old public URL moved permanently |
| 302 | Found | Temporary alternate URL |
| 303 | See Other | Redirect to a GET confirmation page after POST |
| 304 | Not Modified | Reuse a cached representation after validation |
| 307 | Temporary Redirect | Temporary relocation preserving method |
| 308 | Permanent Redirect | Permanent relocation preserving method |
| 400 | Bad Request | Malformed request |
| 401 | Unauthorized | Missing or invalid authentication credentials |
| 403 | Forbidden | User is denied access |
| 404 | Not Found | Resource absent or its existence concealed |
| 405 | Method Not Allowed | Resource does not support the request method |
| 408 | Request Timeout | Complete request was not received within the allowed time |
| 409 | Conflict | Duplicate record conflicts with existing state |
| 413 | Content Too Large | Upload exceeds configured limit |
| 415 | Unsupported Media Type | Endpoint rejects submitted content format |
| 422 | Unprocessable Content | Valid syntax but invalid instructions |
| 429 | Too Many Requests | Request rate exceeds limit |
| 500 | Internal Server Error | Unexpected application exception |
| 501 | Not Implemented | Required functionality unsupported |
| 502 | Bad Gateway | Gateway receives an invalid upstream response |
| 503 | Service Unavailable | Service temporarily unable to process requests |
| 504 | Gateway Timeout | Gateway waits too long for upstream |

The table combines course concepts and independently selected additional codes. RFC 9110 specifies that 401 responses carry a WWW-Authenticate challenge and 405 responses carry an Allow header. A 403 need not imply the user was authenticated. A 404 may intentionally conceal a forbidden resource. 301/302 may permit POST-to-GET conversion by clients, unlike 307/308. A 408 is distinct from a 504. A status code alone cannot establish that a resource is protected or that a vulnerability exists.

## 4. Input formats and routing

| Format | Content-Type | Example |
| --- | --- | --- |
| JSON | application/json | API record |
| URL-encoded form | application/x-www-form-urlencoded | Login form |
| Multipart form | multipart/form-data | Photo upload with form fields |
| Raw binary | application/octet-stream | Binary payload |
| Plain text | text/plain | Text message |

JSON means JavaScript Object Notation; binary means arbitrary bytes; multipart boundaries separate sections of a message; MIME/media type tells the recipient how to interpret content. Never trust content type, extension, filename or user identity merely because the client provides it. Enforce schema, size, authentication, authorization and upload storage controls on the server.

## 5. cURL commands and output

The lesson demonstrates HEAD and GET against the HTB Academy public page. Its dated example output is historical, not a result from this session. The following original local examples assume an owned service running on port 5000:

```bash
curl -I http://127.0.0.1:5000/
curl http://127.0.0.1:5000/
curl -i http://127.0.0.1:5000/
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5000/
```

-I (uppercase) sends HEAD and displays headers; plain curl sends GET and prints the response body; -i includes response headers alongside body; -s disables progress meter; -S shows errors in silent mode; -o /dev/null discards the body; -w prints a formatted result; http_code is the response status value. On PowerShell use curl.exe explicitly and NUL instead of /dev/null for the final example. Avoid -k for real HTTPS; certificate validation is a security boundary. -L follows redirects when desired; inspect the destination and avoid forwarding secrets to untrusted hosts.

A body containing HTML is the delivered page source, not necessarily the DOM after browser JavaScript runs. It is not private PHP/Python server source code. A Server header is optional and may be modified; it is not reliable proof of product, version or vulnerability.

## 6. Server technologies

### Apache HTTP Server
Free, open-source HTTP server, configurable MPMs and loadable modules. PHP can be integrated through mod_php or PHP-FPM via FastCGI; mod_php is not universally required. CGI is Common Gateway Interface, a mechanism to invoke external programs. Apache is not preinstalled on every Linux distribution. See [complete Apache guide](Web-Servers/01-Apache-HTTP-Server.md).

### NGINX
Free open-source edition with event-driven workers, reverse proxying, load balancing and static hosting. Nonblocking I/O lets workers manage many connections efficiently; actual performance depends on workload. See [complete NGINX guide](Web-Servers/02-NGINX.md).

### IIS
Windows web server with application pools, request filtering and integration with Windows Authentication and Active Directory (AD), a directory service for organizational identities and resources. Integrated authentication may enable single sign-on (SSO) in appropriate domain and browser environments; automatic sign-in is not guaranteed. FTP is a separate file-transfer protocol and may be provided through additional IIS components; plain FTP is not encrypted. See [complete IIS guide](Web-Servers/03-Microsoft-IIS.md).

### Apache Tomcat and Node.js
Tomcat is a Java servlet container capable of HTTP service, distinct from Apache HTTP Server. Node.js is a JavaScript runtime that can create HTTP servers using its built-in HTTP module, rather than a standalone preconfigured web server product. See [Tomcat guide](Web-Servers/04-Apache-Tomcat.md) and [Node.js guide](Web-Servers/05-NodeJS.md).

## 7. Original application example — resource creation

Illustrative Flask route, not a patch to UniTrack:

```python
from flask import Flask, jsonify, url_for

app = Flask(__name__)
records = {}

@app.post("/api/demo-records")
def create_record():
    record_id = len(records) + 1
    records[record_id] = {"id": record_id}
    return jsonify(records[record_id]), 201, {
        "Location": url_for("get_record", record_id=record_id)
    }

@app.get("/api/demo-records/<int:record_id>")
def get_record(record_id):
    if record_id not in records:
        return jsonify(error="Not found"), 404
    return jsonify(records[record_id])
```

Flask maps methods and routes to functions; jsonify serializes JSON; url_for builds the resource URI; the return tuple sets response data, status and headers; int: converts the path parameter to an integer. The local in-memory store is demonstration-only, not concurrency-safe or persistent. Production requires authentication, authorization, input validation, atomic database transactions and a supported WSGI server.

A client requesting a creation endpoint should check the status and resource identifier. A subsequent GET can verify that the resource exists and is accessible to the authorized user. A success status is not proof of durable storage or correct permissions.

## 8. Real-world security and project connections

UniTrack: return suitable codes for login, attendance records, duplicate scans and missing records. For protected resources, validate session and role on the server, use CSRF protection where appropriate, validate file uploads, and avoid exposing stack traces. ProTrack-MX: Supabase API responses must be interpreted alongside authenticated user context and RLS policies; a client-side route guard is not authorization. Avoid logging tokens or student data.

For authorized assessment, compare expected and actual codes, response bodies and relevant headers with the intended account and resource. Test allowed versus disallowed actions only within scope. A 200 may contain an error page, a 302 may be a login redirect, and a 403 is not by itself proof that every access path is protected. Avoid unsafe retries of POST operations; use idempotency controls where appropriate. Rate limits, TLS, patching, safe proxy headers, and restricted upstream exposure provide defense in depth.
