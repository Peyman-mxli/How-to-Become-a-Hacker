# HTTP proxies, Squid and explicit/interception configuration

A forward proxy represents clients. HTTP requests may include absolute target URI; CONNECT requests a tunnel to a host/port, usually carrying opaque TLS after establishment. 407 requests proxy authentication. Explicit clients use configured proxy; interception uses authorized network redirection. A proxy does not need to decrypt every payload. Squid is a free/open-source caching forward proxy with ACLs and logging. [Official downloads](https://www.squid-cache.org/Versions/), [configuration](https://www.squid-cache.org/Doc/config/), [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110).

Optional isolated Ubuntu VM setup: sudo apt update; sudo apt install squid. Package may start service; no install needed today. Before any activation, restrict listener to intended interface, restrict authorized clients/destinations, and deny by default; never expose an open proxy. Config commonly /etc/squid/squid.conf; squid -v reports version; sudo squid -k parse validates configuration without intentionally reloading. Illustrative policy: approved staff -> approved software repository allow; guest -> internal service deny. ACL evaluation order matters. Avoid shared caching of private/authenticated data. For local HTTP requests use a dedicated approved proxy configuration and avoid storing credentials in environment variables.

Windows netsh winhttp show proxy is read-only and applies to WinHTTP; Firefox supports separate settings and managed policies. PAC selects proxy/direct according to policy; Winsock alone is not proxy awareness. Troubleshoot 407 authentication, 403 policy, DNS, listener reachability and certificate trust. Explicit proxy plus egress filtering improves visibility; privacy, logging and endpoint controls remain necessary. UniTrack can use approved staff proxy policy; ProTrack-MX cloud HTTPS must remain authenticated. No install or execution.
